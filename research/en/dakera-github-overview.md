Primary-source notes on the Dakera-AI GitHub organization (https://github.com/Dakera-AI) for the project README. ## TL;DR

- Dakera is a self-hosted AI-agent memory server: a single Rust binary (distributed as the `ghcr.io/dakera-ai/dakera` Docker image) exposing REST on port 3000 and gRPC on 50051, with vector (HNSW), BM25 full-text, hybrid, and knowledge-graph retrieval built in [source: https://github.com/Dakera-AI/dakera-deploy README, "Why Dakera?"].
- The whole memory surface is plain JSON over HTTP under `/v1/...`: store / recall / search / get / update / forget, plus batch, sessions, consolidation, knowledge-graph, namespaces, and admin-key endpoints — documented end-to-end in the deploy repo's REST API guide [source: https://github.com/Dakera-AI/dakera-deploy/blob/main/examples/api-notes.md].
- Embeddings are generated server-side by an ONNX engine (default model `bge-large`, 1024d; cross-encoder rerank `bge-reranker-v2-m3`; GLiNER NER) — no OpenAI/embedding API key exists anywhere in the documented config, and air-gapped operation is explicitly supported [source: https://github.com/Dakera-AI/dakera-py/blob/main/README.md; https://github.com/Dakera-AI/dakera-deploy/blob/main/examples/environment-variables.md; dakera-deploy README telemetry section].
- Isolation is per-`agent_id`: each agent maps to an internal namespace (`_dakera_agent_{agent_id}`) that other agents cannot see; explicit namespaces and namespace-scoped API keys are also first-class [source: api-notes.md "Authentication & scopes" / "Conventions"].
- LoCoMo: Dakera publishes its own results — 88.2% Recall@20 (v0.11.107, 1,536 of 1,540 questions, adversarial category excluded), with per-category numbers — on dakera.ai/benchmark and in every repo README badge. The number is LLM-judged retrieval recall, not QA accuracy, and Dakera itself says it is not directly rankable against Zep/Mem0 QA-accuracy claims [source: https://dakera.ai/benchmark].

## 1. What is Dakera — architecture, deployment, API surface, auth

**Architecture.** Dakera is a client-server memory platform: a self-hosted server ("agent-native memory platform... A single self-hosted Rust binary gives you vector search, hybrid retrieval (BM25 + HNSW), knowledge graphs, session management, and built-in embeddings. No external dependencies.") plus SDKs/CLI/MCP clients [source: https://github.com/Dakera-AI/dakera-deploy/blob/main/README.md, "Why Dakera?"]. The server's Docker image builds a Cargo workspace with crates `api`, `common`, `storage`, `engine`, `inference`, `client`, `cli`, `mcp`, `dashboard`, and ships one binary `dakera` (`CMD ["dakera"]`) [source: https://github.com/Dakera-AI/dakera-deploy/blob/main/docker/Dockerfile, lines ~45–53 and ~131–167]. The server source repo `Dakera-AI/dakera` is referenced by PR links in the SDK changelog (e.g. `https://github.com/Dakera-AI/dakera/pull/767`) [source: https://github.com/Dakera-AI/dakera-py/blob/main/CHANGELOG.md, v0.11.98 entry] but returns 404 on the GitHub API, i.e. it is not public [source: https://api.github.com/repos/Dakera-AI/dakera, checked 2026-09-27].

**Org layout.** The org has 19 public repos: `dakera-deploy` (Docker/K8s/Helm), `dakera-helm`, `dakera-py` (Python SDK), `dakera-js` (TS SDK), `dakera-go`, `dakera-rs` (Rust SDK), `dakera-cli` (Rust `dk` CLI), `dakera-mcp` (Rust MCP server), framework integrations (`dakera-langchain`, `dakera-langchain-js`, `dakera-crewai`, `dakera-autogen`, `dakera-llamaindex`, `dakera-ai-sdk`, `strands-dakera`), and packaging repos (`homebrew-tap`, `apt-repo`, `rpm-repo`) [source: https://api.github.com/orgs/Dakera-AI/repos].

**Deployment.**
- Docker one-liner: `docker run -d --name dakera -p 3000:3000 -e DAKERA_ROOT_API_KEY=dk-mykey ghcr.io/dakera-ai/dakera:latest`, health check `curl http://localhost:3000/health` → `{"status":"ok"}` [source: https://github.com/Dakera-AI/dakera-py/blob/main/README.md, "Run Dakera"].
- Compose profiles in `dakera-deploy`: local (single container, in-memory, auth disabled), dev (MinIO), default (full single node + MinIO, `DAKERA_AUTH_ENABLED=true`, `DAKERA_ROOT_API_KEY` required — compose refuses to start without it), HA (3-node cluster behind Traefik with gossip clustering, `DAKERA_CLUSTER_*` env vars), plus Prometheus/Grafana monitoring and a dashboard service [source: https://github.com/Dakera-AI/dakera-deploy/blob/main/README.md, "Zero to Running in 5 Minutes" / profiles; docker/docker-compose.yml lines 32–33 (`DAKERA_AUTH_ENABLED=${DAKERA_AUTH_ENABLED:-true}`, `DAKERA_ROOT_API_KEY` required)].
- Kubernetes manifests + Helm chart [source: dakera-deploy README, "Directory Structure" (`k8s/`); https://github.com/Dakera-AI/dakera-helm].
- Ports: REST `3000` (`DAKERA_PORT`), gRPC `50051` (`DAKERA_GRPC_PORT`), bind host `DAKERA_HOST=0.0.0.0` [source: api-notes.md "Base URL & versioning"].
- Runs in-memory by default (`DAKERA_STORAGE=memory`), S3/MinIO for persistence, optional RocksDB L2 cache and L1→L2→L3 tiered storage [source: https://github.com/Dakera-AI/dakera-deploy/blob/main/examples/environment-variables.md].
- **No public binary distribution of the server itself**: the deploy Dockerfile builds from the private source repo and tells external users to use the prebuilt GHCR image [source: dakera-deploy docker/Dockerfile header comment]. Prebuilt binaries exist only for client tools: `dk` CLI v0.7.1 release ships `dk-aarch64-apple-darwin.tar.gz`, `dk-x86_64-apple-darwin.tar.gz`, `dk-x86_64-unknown-linux-gnu.tar.gz`, `dk-x86_64-pc-windows-msvc.zip` [source: https://github.com/Dakera-AI/dakera-cli/releases/tag/v0.7.1 assets], installed via `brew install dakera-ai/tap/dk` [source: https://github.com/Dakera-AI/homebrew-tap/blob/main/Formula/dk.rb].

**API surface** (all under `/v1/`, JSON over HTTP; verified against engine v0.11.108 per api-notes header) [source: https://github.com/Dakera-AI/dakera-deploy/blob/main/examples/api-notes.md unless noted]:
- Write: `POST /v1/memory/store` (fields `agent_id`, `content`, `memory_type` default `episodic`, `importance` default 0.5, `tags`, `session_id`, `metadata`, `ttl_seconds`, `expires_at`, `id`), `POST /v1/memories/store/batch` (1–1000 items, single embedding pass), `PUT /v1/memory/update/{id}?agent_id=...` (re-embeds on content change), `POST /v1/memory/importance`, `POST /v1/memory/forget` (filter-required delete: `memory_ids`/`memory_type`/`session_id`/`tags`/`below_importance`), `DELETE /v1/memories/forget/batch`.
- Read: `POST /v1/memory/recall` (`query`, `agent_id`, `top_k` default 10, `memory_type`, `tags`, `min_importance`, `routing` = `auto|vector|bm25|hybrid`, `rerank` default true, `since`/`until`, `include_associated`), `POST /v1/memory/search` (browse/filter, no access boost), `GET /v1/memory/get/{id}`, `POST /v1/memories/recall/batch` (filter-only), `GET /v1/agents/{agent_id}/memories`.
- Knowledge/consolidation family: `POST /v1/memory/consolidate` (DBSCAN/greedy clustering, `dry_run`), agent-scoped consolidation + `/v1/agents/{agent_id}/consolidation/log` and `/config`, `POST /v1/knowledge/summarize`, `POST /v1/knowledge/deduplicate` [source: api-notes.md + https://github.com/Dakera-AI/dakera-py/blob/main/src/dakera/client.py, `summarize`/`deduplicate` methods ~line 2202].
- Knowledge graph: `GET /v1/memories/{id}/graph` (traverse, edge types `related_to|shares_entity|precedes|linked_by`), `GET /v1/memories/{source_id}/path`, `POST /v1/memories/{source_id}/links`, `GET /v1/agents/{agent_id}/graph/export`, `GET /v1/knowledge/query` (KG-2 filter DSL with BFS from a root) [source: client.py `memory_graph`/`memory_path`/`memory_link`/`agent_graph_export`/`knowledge_query`].
- Feedback: `POST /v1/memories/{memory_id}/feedback` (upvote +0.05–0.10 importance, downvote −0.15, flag accelerates decay), feedback history/health, TIF evaluation [source: api-notes.md "Updating memories"; client.py `memory_feedback`/`feedback_memory`/`evaluate_tif`].
- Sessions: start/end endpoints; sessions live in a shared reserved namespace `_dakera_sessions` [source: api-notes.md "Conventions"].
- Vector-namespace ops (raw API beneath the memory layer): `upsert`, `query`, `fetch`, `delete`, bulk ops, `upsert-text`/`query-text` (server-side auto-embedding), `fulltext/index`, `fulltext/search`, `hybrid` under `/v1/namespaces/{ns}/...` [source: https://github.com/Dakera-AI/dakera-py/blob/main/src/dakera/client.py, methods ~lines 364–900].
- Ops/health: `GET /health`, `/health/live`, `/health/ready`, `/metrics`, `GET /v1/ops/metrics` (admin), `GET /v1/ops/stats` [source: api-notes.md "Health & readiness"].

**Auth model.** Auth is on when `DAKERA_AUTH_ENABLED=true` (production default; local compose profile disables it). Key is supplied via `X-API-Key` header (or `Authorization: Bearer`; `?api_key=` only as SSE fallback). Scopes are hierarchical: `read ⊂ write ⊂ admin ⊂ super_admin` — `read` = recall/search/get/list/stats/graph reads; `write` adds store/update/forget/consolidate/feedback; `admin` adds key management and ops metrics; `super_admin` = all namespaces, no expiry. The `DAKERA_ROOT_API_KEY` root key is a `super_admin` key. Additional scoped keys are minted via `/v1/admin/keys` or per-namespace via `/v1/namespaces/{ns}/keys`; keys are stored as SHA-256 hashes and the plaintext is shown once; a key can be restricted to specific namespaces (403 outside them) [source: api-notes.md "Authentication & scopes"]. SDK mirrors this: `create_key`/`list_keys`/`rotate_key`/... on `/admin/keys` [source: client.py ~line 2627] and `create_namespace_key(namespace, name, expires_in_days)` on `/v1/namespaces/{ns}/keys` (SEC-1) [source: client.py ~line 2885].

## 2. Is the core a Rust binary?

**Yes — the server is a single Rust binary, and the org's client tooling is Rust too.**

- Server: the production Dockerfile builds from Rust source — `FROM rust:1.97-bookworm AS builder`, a Cargo workspace with `crates/{api,common,storage,engine,inference,client,cli,mcp,dashboard}`, thin-LTO release profile, then the runtime stage copies `/usr/local/bin/dakera` into `debian:bookworm-slim` and runs `CMD ["dakera"]` [source: https://github.com/Dakera-AI/dakera-deploy/blob/main/docker/Dockerfile].
- The deploy README states it in prose: "A single self-hosted Rust binary gives you vector search, hybrid retrieval (BM25 + HNSW), knowledge graphs, session management, and built-in embeddings. No external dependencies." [source: https://github.com/Dakera-AI/dakera-deploy/blob/main/README.md, "Why Dakera?"].
- The `dakera-py` README footer: "Built with Rust. Single binary. Zero external dependencies." [source: https://github.com/Dakera-AI/dakera-py/blob/main/README.md, last line].
- Client tools are Rust crates: `dakera-cli` is `lang=Rust` with `Cargo.toml` (`[package] name = "dk"`, depends on `dakera-client = "0.11"`, tokio) and publishes to crates.io as `dakera-cli` with prebuilt binaries on GitHub releases [source: https://github.com/Dakera-AI/dakera-cli/blob/main/Cargo.toml; https://api.github.com/repos/Dakera-AI/dakera-cli, `language: Rust`; v0.7.1 release assets]. `dakera-mcp` is likewise Rust (`crates.io/crates/dakera-mcp`, `cargo install dakera-mcp`, prebuilt musl/darwin/msvc binaries) [source: https://github.com/Dakera-AI/dakera-mcp/blob/main/README.md, Install section].
- Caveat: the **server source is not public** — the `Dakera-AI/dakera` repo 404s on the API (private), so "Rust core" is proven by the deploy Dockerfile/README claims and image, not by readable server source [source: https://api.github.com/repos/Dakera-AI/dakera → Not Found, checked 2026-09-27].

## 3. Self-hosting without external models (README headline claim)

**Claim verified: retrieval/embedding runs locally; no external LLM or embedding API key is required for the documented feature set.**

- Marketing claim: comparison table row "Embeddings — Built-in — no OpenAI key needed" vs. competitors "Requires external embedding API" [source: https://github.com/Dakera-AI/dakera-py/blob/main/README.md, "Why Dakera?" table].
- Mechanism: "Text Auto-Embedding — server-side embedding generation (no local model needed)" (client-side wording — the server does it) [source: dakera-py README features list]. The embedding models are served by the server's ONNX inference engine: `EmbeddingModel` enum = `bge-large` (default, 1024d), `minilm`, `bge-small`, `e5-small` (384d), `modernbert-embed-base` (768d), `gte-modernbert-base` (768d) [source: https://github.com/Dakera-AI/dakera-py/blob/main/src/dakera/models.py, `class EmbeddingModel`; CHANGELOG 0.12.7 for the ModernBERT additions]. Reranking is a server-side cross-encoder `bge-reranker-v2-m3` [source: dakera-py CHANGELOG CE-13 entry]. Entity extraction is GLiNER zero-shot NER server-side with rule-based fallback when the model is not yet downloaded [source: https://github.com/Dakera-AI/dakera-py/blob/main/src/dakera/client.py, `configure_namespace_ner` docstring, "Requires CE-4 (GLiNER) on the server"].
- Models are cached locally: the server image sets `HF_HOME=/home/dakera/.cache/huggingface` and creates `/data/models` [source: dakera-deploy docker/Dockerfile runtime stage].
- Config surface check: the complete env-var reference contains **no** embedding/LLM/API-key variables — only auth (`DAKERA_ROOT_API_KEY`), storage (S3/MinIO), cache, cluster, and limits [source: https://github.com/Dakera-AI/dakera-deploy/blob/main/examples/environment-variables.md, entire file].
- Air-gapped: "Fully air-gapped operation is supported" (telemetry is opt-out via `DAKERA_TELEMETRY=off` / `DO_NOT_TRACK=1`) [source: dakera-deploy README, telemetry section].
- Benchmark framing corroborates: "no LLM in the retrieval path" for LoCoMo retrieval [source: https://dakera.ai/benchmark].
- Nuances worth flagging in a README: (a) the optional `/v1/knowledge/summarize` endpoint and the per-namespace `extractor` config (`provider`, `model`, `base_url` fields) suggest a pluggable extractor/summarizer provider that could point at an external LLM [source: client.py `get_namespace_extractor` returns `provider/model/base_url`; `summarize` method]. Whether summarize requires an external LLM or has a local fallback is **not documented in the inspected sources** [INFERENCE]. (b) The gRPC + HTTP server and ONNX/GLiNER/HF-cached models all run inside the single image; nothing in the deploy or SDK docs requires an OpenAI/Anthropic key [source: environment-variables.md; Dockerfile]. (c) Historical note: embedding upgrades happen server-side via background ONNX re-embed jobs (`/v1/admin/reembed/static-count`, `drain_reembed`) — still local [source: dakera-py CHANGELOG 0.12.x entries].

## 4. Namespaces — how isolation works

- **Agent-level isolation is the primary model.** "The agent is the unit of isolation. Every memory belongs to an `agent_id`, which maps to an internal namespace (`_dakera_agent_{agent_id}`). Memories under different `agent_id`s cannot see each other. Sessions live in a shared reserved namespace (`_dakera_sessions`)." [source: https://github.com/Dakera-AI/dakera-deploy/blob/main/examples/api-notes.md, "Conventions"]. Every memory call requires `agent_id` (`store_memory(agent_id=...)`, `recall(agent_id=...)`) [source: https://github.com/Dakera-AI/dakera-py/blob/main/src/dakera/client.py, `store_memory`/`recall` signatures].
- **Explicit namespaces are also first-class**: `list_namespaces`/`get_namespace`/`create_namespace`/`configure_namespace` on `/v1/namespaces[/{ns}]`, with `NamespaceInfo { name, vector_count, dimensions, index_type, created_at, updated_at, metadata }` [source: client.py ~lines 905–1000; https://github.com/Dakera-AI/dakera-py/blob/main/src/dakera/models.py `class NamespaceInfo`]. Raw vector/fulltext/hybrid operations are all namespace-scoped (`/v1/namespaces/{ns}/query`, `/upsert-text`, `/hybrid`, ...) [source: client.py ~lines 364–900].
- **Scoped keys bind isolation to auth**: keys may be restricted to specific namespaces (403 outside the allowed set); per-namespace keys are created via `/v1/namespaces/{ns}/keys` [source: api-notes.md "Authentication & scopes"; client.py `create_namespace_key` (SEC-1)].
- **Per-namespace policy knobs**: memory policy rate limits (per-namespace store/recall), vector quotas (413 "Namespace vector quota exceeded"), per-namespace NER config (`extract_entities`, `entity_types`) and extractor config [source: api-notes.md error table + rate limiting + client.py `configure_namespace_ner`/`get_namespace_entity_config`].

## 5. Team / multi-agent work

- The only explicit multi-agent statement is the use-case table: "Multi-agent pipelines — Shared cross-agent memory, session isolation per agent, importance-ranked recall" [source: https://github.com/Dakera-AI/dakera-deploy/blob/main/README.md, "Used For"]. Mechanically this means agents sharing an `agent_id`/namespace share memory, while per-agent namespaces keep them isolated [source: api-notes.md "Conventions"; INFERENCE on the sharing mechanism — no doc shows a dedicated "share with team" primitive].
- Session machinery supports multi-session agents: session-scoped HNSW pre-filter and BM25 session pre-filter prevent cross-session bleed ("Session-scoped queries no longer bleed cross-session results") [source: https://github.com/Dakera-AI/dakera-py/blob/main/CHANGELOG.md, v0.11.36 entry, CE-52/CE-53].
- Knowledge-graph association gives cross-memory/cross-agent structure: edges `related_to`, `shares_entity`, `precedes`, `linked_by`; `memory_link` creates explicit edges; `knowledge_query` (KG-2) does BFS with edge-type filters; `agent_graph_export` exports the whole agent graph [source: client.py `memory_graph`/`memory_link`/`knowledge_query`/`agent_graph_export` docstrings]. Per-namespace GLiNER entity extraction feeds entity-scoped vector search, e.g. `{"tags": F.array_contains("entity:PERSON:alice")}` [source: dakera-py CHANGELOG, v0.11.46 ArrayContains entry].
- Consolidation is the "team hygiene" story: `POST /v1/memory/consolidate` (DBSCAN or greedy clustering, threshold, dry-run), agent-scoped DBSCAN consolidation with deprecation of duplicates + anchor memories, consolidation log/config endpoints, plus `knowledge/summarize` and `knowledge/deduplicate` [source: client.py `consolidate`/`consolidate_agent`/`get_consolidation_log`/`patch_consolidation_config`/`summarize`/`deduplicate`].
- No documented team/roles/workspace feature beyond namespaces + scoped keys in the inspected sources [INFERENCE: none found in org READMEs, api-notes, or SDK surface].

## 6. Extra features worth advertising

- **Memory types**: `episodic` (default), `semantic`, `procedural`, `working` [source: client.py `store_memory` docstring].
- **Importance + scoring**: importance 0.0–1.0 on store; recall returns `score` (cosine-bounded only on pure vector routing), `weighted_score` (importance-weighted rerank), and `smart_score = w_vec·relevance + w_imp·importance + w_rec·recency + w_freq·frequency`; BM25/hybrid scores are unbounded; `DAKERA_NORMALIZE_RELEVANCE=1` opt-in [source: api-notes.md "Scoring" section]. Feedback nudges importance (upvote/downvote/flag) and decay [source: api-notes.md "Updating memories"].
- **Hybrid routing**: `routing = auto | vector | bm25 | hybrid` on recall, with RRF fusion (`DAKERA_RRF_K` configurable), pseudo-relevance feedback for temporal/inference queries, ML query classifier, BM25 Snowball stemming [source: api-notes.md recall fields; dakera-py CHANGELOG CE-48/CE-49/CE-58/CE-71 entries].
- **Rerank**: cross-encoder reranking (bge-reranker-v2-m3), `rerank=true` default on recall, degrade-gracefully under load [source: api-notes.md recall fields; dakera-py CHANGELOG CE-13].
- **Knowledge graph / associations (COG-2 / KG-2 in dakera-py)**: graph traversal with depth and edge-type filters, shortest path, explicit linking, BFS query DSL, full graph export [source: client.py `memory_graph`/`memory_path`/`memory_link`/`knowledge_query`/`agent_graph_export`; `__init__.py` exports "Knowledge Graph types (internal graph — knowledge.rs)" and "KG-2: Graph Query & Export types"].
- **Neighborhood context**: `include_associated=true` on recall traverses the KG for neighbour memories [source: api-notes.md recall field table].
- **Consolidation family**: clustering dedup (dbscan/greedy), summarize, deduplicate, consolidation logs/config [source: client.py; api-notes.md].
- **Temporal features**: bi-temporal `valid_from` (server v0.11.98+, DAK-7424), auto date extraction into `metadata._dakera_content_date` (v0.11.73+), TTL/`expires_at`, temporal-proximity scoring, memory decay metrics dashboards (v0.8.0+) [source: client.py `store_memory` docstring; api-notes.md store section; dakera-deploy README monitoring section].
- **Batch + streaming**: batch store (1–1000, single embedding pass), batch recall/forget, SSE streaming events (CE-1) [source: api-notes.md; client.py SSE section + `batch_recall`/`batch_forget`].
- **MCP server**: 14 core tools by default (`dakera_store`, `dakera_recall`, `dakera_search`, `dakera_session_start/end`, `dakera_batch_recall`, `dakera_forget`, `dakera_hybrid_search`, `dakera_fulltext_search`, `dakera_knowledge_graph`, `dakera_extract`, `dakera_batch_forget`, + 2 discovery meta-tools), profiles core(14)/admin(32)/power(69)/all(87) to control context cost [source: https://github.com/Dakera-AI/dakera-mcp/blob/main/README.md].
- **Transports**: HTTP + gRPC on every deployment profile [source: dakera-py README comparison table; compose port maps].
- **Ops**: Prometheus metrics, Grafana dashboards (request rates, latency, cache hit ratios, cluster health, decay), 3-node HA with gossip + Traefik, tiered L1/L2/L3 storage, MinIO backup/restore guide [source: dakera-deploy README].

## 7. LoCoMo benchmark

**What LoCoMo is.** "Evaluating Very Long-Term Conversational Memory of LLM Agents" — Maharana, Lee, Tulyakov, Bansal, Barbieri, Fang; arXiv:2402.17753 (Feb 2024), ACL 2024. It introduces a machine-human pipeline generating very long-term dialogues grounded in personas and temporal event graphs, and the LoCoMo dataset: very long-term conversations averaging 300 turns / 9K tokens across up to 35 sessions, with a benchmark covering question answering, event summarization, and multimodal dialogue generation [source: https://arxiv.org/abs/2402.17753, abstract]. Data repo: https://github.com/snap-research/LoCoMo ("ten conversations... annotated for the question-answering and event-summarization tasks") [source: https://github.com/snap-research/LoCoMo README].

**Dakera's published LoCoMo results — they DO publish, on the org's own benchmark page and README badges (all numbers below are Dakera's self-reported figures from that page):**

- Headline: **88.2% Recall@20**, Dakera v0.11.107, evaluated September 2026; "10 conversations, 1,536 evaluated questions, no LLM in the retrieval path"; metric is LLM-judged retrieval recall (ground-truth answer present in top-20 retrieved memories) [source: https://dakera.ai/benchmark].
- Per-category: Cat1 Single-hop **86.9%** (282 questions); Cat2 Multi-hop **85.4%** (321 q); Cat3 Temporal inference **73.9%** (92 q, self-described hardest category); Cat4 Open-domain **91.0%** (841 q). Overall row notes "1,536 (10 conversations)... adversarial category excluded" [source: https://dakera.ai/benchmark, breakdown table].
- Question count reconciliation: LoCoMo has 1,540 QA questions total; 1,536 are evaluated (adversarial category excluded), "We do not use sampled subsets" [source: https://dakera.ai/benchmark, Evaluation methodology]. Repo READMEs variously say "1,536 Q" (dakera-py README) or "1,540 questions" (dakera-deploy README) [source: dakera-py README "Why Dakera?" table; dakera-deploy README "Why Dakera?"].
- Protocol (self-published): ingest via `POST /v1/memory` preserving session boundaries, no preprocessing/summarization; recall via `POST /v1/recall` returning top-20 with HNSW+BM25 hybrid + non-LLM temporal re-ranker; LLM judge scores binary presence using the standard LoCoMo evaluation prompt; 88.2% is the mean across 1,536 questions [source: https://dakera.ai/benchmark, "How we evaluate"].
- Latency claim attached to the same page: server-side P99 < 10 ms on a warm 20k-vector in-memory index (top_k=20, single-threaded, idle 8-core x64 host; ≈16 ms end-to-end) [source: https://dakera.ai/benchmark, "Production latency"].
- Competitor framing (as printed by Dakera, different metric — QA-accuracy, "not directly rankable... context, not a leaderboard"): Letta Filesystem 74.0%, Zep 94.7%, Mem0 92.5%, with both Zep/Mem0 numbers described as actively disputed by the other party [source: https://dakera.ai/benchmark, "How Dakera compares" + "The benchmark dispute"].
