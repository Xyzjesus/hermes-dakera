## TL;DR

- Dakera — self-hosted (на своём сервере) сервер памяти для AI-агентов: один бинарник на Rust (поставляется как Docker-образ `ghcr.io/dakera-ai/dakera`), REST на порту 3000 и gRPC на 50051, со встроенным vector-поиском (HNSW), полнотекстовым BM25, hybrid-поиском и knowledge-graph retrieval [source: https://github.com/Dakera-AI/dakera-deploy README, "Why Dakera?"].
- Вся memory-поверхность — обычный JSON поверх HTTP по путям `/v1/...`: store / recall / search / get / update / forget, плюс эндпоинты для batch, sessions, consolidation, knowledge-graph, namespaces и admin-ключей — документировано от начала до конца в REST API guide репозитория deploy [source: https://github.com/Dakera-AI/dakera-deploy/blob/main/examples/api-notes.md].
- Embeddings генерируются на стороне сервера ONNX-движком (модель по умолчанию `bge-large`, 1024d; cross-encoder rerank `bge-reranker-v2-m3`; GLiNER NER) — в документированной конфигурации нигде нет ключа OpenAI/embedding API, а работа в air-gapped-окружении явно поддерживается [source: https://github.com/Dakera-AI/dakera-py/blob/main/README.md; https://github.com/Dakera-AI/dakera-deploy/blob/main/examples/environment-variables.md; раздел telemetry в README dakera-deploy].
- Изоляция — на уровне `agent_id`: каждый агент отображается на внутренний namespace (`_dakera_agent_{agent_id}`), невидимый для других агентов; явные namespaces и namespace-scoped API-ключи тоже являются полноценными сущностями [source: api-notes.md "Authentication & scopes" / "Conventions"].
- LoCoMo: Dakera публикует собственные результаты — 88.2% Recall@20 (v0.11.107, 1,536 из 1,540 вопросов, adversarial-категория исключена) с разбивкой по категориям — на dakera.ai/benchmark и в бейдже README каждого репозитория. Это retrieval recall, оцениваемый LLM-judge, а не QA accuracy, и сама Dakera говорит, что напрямую ранжировать его против QA-accuracy-заявлений Zep/Mem0 нельзя [source: https://dakera.ai/benchmark].

## 1. Что такое Dakera — архитектура, развёртывание, поверхность API, auth

**Архитектура.** Dakera — клиент-серверная memory-платформа: self-hosted сервер ("agent-native memory platform... A single self-hosted Rust binary gives you vector search, hybrid retrieval (BM25 + HNSW), knowledge graphs, session management, and built-in embeddings. No external dependencies.") плюс SDK/CLI/MCP-клиенты [source: https://github.com/Dakera-AI/dakera-deploy/blob/main/README.md, "Why Dakera?"]. Docker-образ сервера собирает Cargo workspace с крейтами `api`, `common`, `storage`, `engine`, `inference`, `client`, `cli`, `mcp`, `dashboard` и поставляет один бинарник `dakera` (`CMD ["dakera"]`) [source: https://github.com/Dakera-AI/dakera-deploy/blob/main/docker/Dockerfile, строки ~45–53 и ~131–167]. Репозиторий исходников сервера `Dakera-AI/dakera` упоминается в PR-ссылках changelog SDK (например, `https://github.com/Dakera-AI/dakera/pull/767`) [source: https://github.com/Dakera-AI/dakera-py/blob/main/CHANGELOG.md, запись v0.11.98], но на GitHub API отдаёт 404, т.е. он не публичный [source: https://api.github.com/repos/Dakera-AI/dakera, проверено 2026-09-27].

**Состав организации.** В организации 19 публичных репозиториев: `dakera-deploy` (Docker/K8s/Helm), `dakera-helm`, `dakera-py` (Python SDK), `dakera-js` (TS SDK), `dakera-go`, `dakera-rs` (Rust SDK), `dakera-cli` (Rust CLI `dk`), `dakera-mcp` (MCP-сервер на Rust), интеграции с фреймворками (`dakera-langchain`, `dakera-langchain-js`, `dakera-crewai`, `dakera-autogen`, `dakera-llamaindex`, `dakera-ai-sdk`, `strands-dakera`) и репозитории пакетов (`homebrew-tap`, `apt-repo`, `rpm-repo`) [source: https://api.github.com/orgs/Dakera-AI/repos].

**Развёртывание.**
- Docker-однострочник: `docker run -d --name dakera -p 3000:3000 -e DAKERA_ROOT_API_KEY=dk-mykey ghcr.io/dakera-ai/dakera:latest`, health-проверка `curl http://localhost:3000/health` → `{"status":"ok"}` [source: https://github.com/Dakera-AI/dakera-py/blob/main/README.md, "Run Dakera"].
- Профили Compose в `dakera-deploy`: local (один контейнер, in-memory, auth выключен), dev (MinIO), default (полноценный one-node + MinIO, `DAKERA_AUTH_ENABLED=true`, обязателен `DAKERA_ROOT_API_KEY` — без него Compose отказывается стартовать), HA (кластер из 3 узлов за Traefik с gossip-кластеризацией, env-переменные `DAKERA_CLUSTER_*`), плюс мониторинг Prometheus/Grafana и сервис dashboard [source: https://github.com/Dakera-AI/dakera-deploy/blob/main/README.md, "Zero to Running in 5 Minutes" / profiles; docker/docker-compose.yml строки 32–33 (`DAKERA_AUTH_ENABLED=${DAKERA_AUTH_ENABLED:-true}`, `DAKERA_ROOT_API_KEY` обязателен)].
- Манифесты Kubernetes + Helm-чарт [source: README dakera-deploy, "Directory Structure" (`k8s/`); https://github.com/Dakera-AI/dakera-helm].
- Порты: REST `3000` (`DAKERA_PORT`), gRPC `50051` (`DAKERA_GRPC_PORT`), хост привязки `DAKERA_HOST=0.0.0.0` [source: api-notes.md "Base URL & versioning"].
- По умолчанию работает in-memory (`DAKERA_STORAGE=memory`), для персистентности S3/MinIO, опционально L2-кэш RocksDB и ярусное хранилище L1→L2→L3 [source: https://github.com/Dakera-AI/dakera-deploy/blob/main/examples/environment-variables.md].
- **Публичной бинарной поставки самого сервера нет**: Dockerfile из deploy собирается из приватного репозитория исходников и предлагает внешним пользователям готовый GHCR-образ [source: dakera-deploy docker/Dockerfile, комментарий в шапке]. Prebuilt-бинарники есть только у клиентских инструментов: релиз `dk` CLI v0.7.1 содержит `dk-aarch64-apple-darwin.tar.gz`, `dk-x86_64-apple-darwin.tar.gz`, `dk-x86_64-unknown-linux-gnu.tar.gz`, `dk-x86_64-pc-windows-msvc.zip` [source: https://github.com/Dakera-AI/dakera-cli/releases/tag/v0.7.1, assets], установка через `brew install dakera-ai/tap/dk` [source: https://github.com/Dakera-AI/homebrew-tap/blob/main/Formula/dk.rb].

**Поверхность API** (всё под `/v1/`, JSON поверх HTTP; сверено с engine v0.11.108 согласно заголовку api-notes) [source: https://github.com/Dakera-AI/dakera-deploy/blob/main/examples/api-notes.md, если не указано иное]:
- Write: `POST /v1/memory/store` (поля `agent_id`, `content`, `memory_type` по умолчанию `episodic`, `importance` по умолчанию 0.5, `tags`, `session_id`, `metadata`, `ttl_seconds`, `expires_at`, `id`), `POST /v1/memories/store/batch` (1–1000 элементов, один проход embedding), `PUT /v1/memory/update/{id}?agent_id=...` (ре-embedding при изменении content), `POST /v1/memory/importance`, `POST /v1/memory/forget` (удаление только с обязательным фильтром: `memory_ids`/`memory_type`/`session_id`/`tags`/`below_importance`), `DELETE /v1/memories/forget/batch`.
- Read: `POST /v1/memory/recall` (`query`, `agent_id`, `top_k` по умолчанию 10, `memory_type`, `tags`, `min_importance`, `routing` = `auto|vector|bm25|hybrid`, `rerank` по умолчанию true, `since`/`until`, `include_associated`), `POST /v1/memory/search` (просмотр/фильтрация, без access boost), `GET /v1/memory/get/{id}`, `POST /v1/memories/recall/batch` (только фильтры), `GET /v1/agents/{agent_id}/memories`.
- Семейство knowledge/consolidation: `POST /v1/memory/consolidate` (кластеризация DBSCAN/greedy, `dry_run`), consolidation в рамках агента + `/v1/agents/{agent_id}/consolidation/log` и `/config`, `POST /v1/knowledge/summarize`, `POST /v1/knowledge/deduplicate` [source: api-notes.md + https://github.com/Dakera-AI/dakera-py/blob/main/src/dakera/client.py, методы `summarize`/`deduplicate` ~строка 2202].
- Knowledge graph: `GET /v1/memories/{id}/graph` (обход, типы рёбер `related_to|shares_entity|precedes|linked_by`), `GET /v1/memories/{source_id}/path`, `POST /v1/memories/{source_id}/links`, `GET /v1/agents/{agent_id}/graph/export`, `GET /v1/knowledge/query` (filter DSL KG-2 с BFS от корня) [source: client.py `memory_graph`/`memory_path`/`memory_link`/`agent_graph_export`/`knowledge_query`].
- Feedback: `POST /v1/memories/{memory_id}/feedback` (upvote +0.05–0.10 к importance, downvote −0.15, flag ускоряет decay), история/health feedback, TIF-оценка [source: api-notes.md "Updating memories"; client.py `memory_feedback`/`feedback_memory`/`evaluate_tif`].
- Sessions: эндпоинты start/end; сессии живут в общем зарезервированном namespace `_dakera_sessions` [source: api-notes.md "Conventions"].
- Операции над vector-namespace (сырой API под memory-слоем): `upsert`, `query`, `fetch`, `delete`, bulk-операции, `upsert-text`/`query-text` (авто-embedding на стороне сервера), `fulltext/index`, `fulltext/search`, `hybrid` под `/v1/namespaces/{ns}/...` [source: https://github.com/Dakera-AI/dakera-py/blob/main/src/dakera/client.py, методы ~строки 364–900].
- Ops/health: `GET /health`, `/health/live`, `/health/ready`, `/metrics`, `GET /v1/ops/metrics` (admin), `GET /v1/ops/stats` [source: api-notes.md "Health & readiness"].

**Модель auth.** Auth включён при `DAKERA_AUTH_ENABLED=true` (умолчание в production; профиль local в Compose его выключает). Ключ передаётся через заголовок `X-API-Key` (или `Authorization: Bearer`; `?api_key=` — только как fallback для SSE). Скоупы иерархические: `read ⊂ write ⊂ admin ⊂ super_admin` — `read` = операции чтения recall/search/get/list/stats/graph; `write` добавляет store/update/forget/consolidate/feedback; `admin` добавляет управление ключами и ops-метрики; `super_admin` = все namespaces, без срока действия. Корневой ключ `DAKERA_ROOT_API_KEY` — ключ уровня `super_admin`. Дополнительные скоуп-ключи выпускаются через `/v1/admin/keys` или per-namespace через `/v1/namespaces/{ns}/keys`; ключи хранятся как SHA-256-хэши, и plaintext показывается один раз; ключ можно ограничить конкретными namespaces (вне их — 403) [source: api-notes.md "Authentication & scopes"]. SDK повторяет это: `create_key`/`list_keys`/`rotate_key`/... на `/admin/keys` [source: client.py ~строка 2627] и `create_namespace_key(namespace, name, expires_in_days)` на `/v1/namespaces/{ns}/keys` (SEC-1) [source: client.py ~строка 2885].

## 2. Ядро — это бинарник на Rust?

**Да — сервер представляет собой один бинарник на Rust, и клиентские инструменты организации тоже написаны на Rust.**

- Server: production-Dockerfile собирается из исходников Rust — `FROM rust:1.97-bookworm AS builder`, Cargo workspace с `crates/{api,common,storage,engine,inference,client,cli,mcp,dashboard}`, release-профиль с thin-LTO, затем runtime-стадия копирует `/usr/local/bin/dakera` в `debian:bookworm-slim` и запускает `CMD ["dakera"]` [source: https://github.com/Dakera-AI/dakera-deploy/blob/main/docker/Dockerfile].
- В README deploy это заявлено прямым текстом: "A single self-hosted Rust binary gives you vector search, hybrid retrieval (BM25 + HNSW), knowledge graphs, session management, and built-in embeddings. No external dependencies." [source: https://github.com/Dakera-AI/dakera-deploy/blob/main/README.md, "Why Dakera?"].
- Подвал README `dakera-py`: "Built with Rust. Single binary. Zero external dependencies." [source: https://github.com/Dakera-AI/dakera-py/blob/main/README.md, последняя строка].
- Клиентские инструменты — Rust-крейты: `dakera-cli` — это `lang=Rust` с `Cargo.toml` (`[package] name = "dk"`, зависимость `dakera-client = "0.11"`, tokio), публикуется на crates.io как `dakera-cli` с prebuilt-бинарниками на GitHub releases [source: https://github.com/Dakera-AI/dakera-cli/blob/main/Cargo.toml; https://api.github.com/repos/Dakera-AI/dakera-cli, `language: Rust`; assets релиза v0.7.1]. `dakera-mcp` тоже на Rust (`crates.io/crates/dakera-mcp`, `cargo install dakera-mcp`, prebuilt-бинарники musl/darwin/msvc) [source: https://github.com/Dakera-AI/dakera-mcp/blob/main/README.md, раздел Install].
- Оговорка: **исходники сервера не публичны** — репозиторий `Dakera-AI/dakera` на API отдаёт 404 (приватный), так что «Rust-ядро» подтверждается заявлениями в Dockerfile/README deploy и образом, а не читаемыми исходниками сервера [source: https://api.github.com/repos/Dakera-AI/dakera → Not Found, проверено 2026-09-27].

## 3. Self-hosting без внешних моделей (заявка из заголовка README)

**Заявка подтверждена: retrieval/embedding выполняются локально; для документированного набора функций внешний LLM или ключ embedding API не требуется.**

- Маркетинговая заявка: строка таблицы сравнения "Embeddings — Built-in — no OpenAI key needed" против конкурентов "Requires external embedding API" [source: https://github.com/Dakera-AI/dakera-py/blob/main/README.md, таблица "Why Dakera?"].
- Механика: "Text Auto-Embedding — server-side embedding generation (no local model needed)" (формулировка со стороны клиента — генерирует сервер) [source: dakera-py README, список features]. Модели embedding раздаёт ONNX inference-движок сервера: enum `EmbeddingModel` = `bge-large` (по умолчанию, 1024d), `minilm`, `bge-small`, `e5-small` (384d), `modernbert-embed-base` (768d), `gte-modernbert-base` (768d) [source: https://github.com/Dakera-AI/dakera-py/blob/main/src/dakera/models.py, `class EmbeddingModel`; CHANGELOG 0.12.7 о добавлении ModernBERT]. Rerank — серверный cross-encoder `bge-reranker-v2-m3` [source: dakera-py CHANGELOG, запись CE-13]. Извлечение сущностей — GLiNER zero-shot NER на стороне сервера с fallback на правила, если модель ещё не скачана [source: https://github.com/Dakera-AI/dakera-py/blob/main/src/dakera/client.py, docstring `configure_namespace_ner`, "Requires CE-4 (GLiNER) on the server"].
- Модели кэшируются локально: образ сервера задаёт `HF_HOME=/home/dakera/.cache/huggingface` и создаёт `/data/models` [source: dakera-deploy docker/Dockerfile, runtime-стадия].
- Проверка поверхности конфигурации: полный справочник env-переменных **не содержит** переменных embedding/LLM/API-ключей — только auth (`DAKERA_ROOT_API_KEY`), storage (S3/MinIO), cache, cluster и лимиты [source: https://github.com/Dakera-AI/dakera-deploy/blob/main/examples/environment-variables.md, весь файл].
- Air-gapped: "Fully air-gapped operation is supported" (telemetry отключается через `DAKERA_TELEMETRY=off` / `DO_NOT_TRACK=1`) [source: README dakera-deploy, раздел telemetry].
- Согласуется с подачей бенчмарка: "no LLM in the retrieval path" для LoCoMo retrieval [source: https://dakera.ai/benchmark].
- Нюансы, которые стоит отметить в README: (a) опциональный эндпоинт `/v1/knowledge/summarize` и per-namespace конфиг `extractor` (поля `provider`, `model`, `base_url`) намекают на подключаемый extractor/summarizer-провайдер, который можно направить на внешний LLM [source: client.py, `get_namespace_extractor` возвращает `provider/model/base_url`; метод `summarize`]. Требует ли summarize внешнего LLM или имеет локальный fallback, **в изученных источниках не документировано** [INFERENCE]. (b) Сервер gRPC + HTTP и модели ONNX/GLiNER/кэш HF работают внутри одного образа; ни документация deploy, ни документация SDK не требуют ключа OpenAI/Anthropic [source: environment-variables.md; Dockerfile]. (c) Историческая заметка: обновления embedding выполняются на сервере фоновыми ONNX re-embed-задачами (`/v1/admin/reembed/static-count`, `drain_reembed`) — по-прежнему локально [source: dakera-py CHANGELOG, записи 0.12.x].

## 4. Namespaces — как устроена изоляция

- **Изоляция на уровне агента — основная модель.** "The agent is the unit of isolation. Every memory belongs to an `agent_id`, which maps to an internal namespace (`_dakera_agent_{agent_id}`). Memories under different `agent_id`s cannot see each other. Sessions live in a shared reserved namespace (`_dakera_sessions`)." [source: https://github.com/Dakera-AI/dakera-deploy/blob/main/examples/api-notes.md, "Conventions"]. Каждый вызов memory требует `agent_id` (`store_memory(agent_id=...)`, `recall(agent_id=...)`) [source: https://github.com/Dakera-AI/dakera-py/blob/main/src/dakera/client.py, сигнатуры `store_memory`/`recall`].
- **Явные namespaces — тоже полноценные сущности**: `list_namespaces`/`get_namespace`/`create_namespace`/`configure_namespace` на `/v1/namespaces[/{ns}]`, с `NamespaceInfo { name, vector_count, dimensions, index_type, created_at, updated_at, metadata }` [source: client.py ~строки 905–1000; https://github.com/Dakera-AI/dakera-py/blob/main/src/dakera/models.py `class NamespaceInfo`]. Сырые vector/fulltext/hybrid-операции скоупятся по namespace (`/v1/namespaces/{ns}/query`, `/upsert-text`, `/hybrid`, ...) [source: client.py ~строки 364–900].
- **Скоуп-ключи связывают изоляцию с auth**: ключи можно ограничить конкретными namespaces (вне разрешённого набора — 403); per-namespace ключи создаются через `/v1/namespaces/{ns}/keys` [source: api-notes.md "Authentication & scopes"; client.py `create_namespace_key` (SEC-1)].
- **Per-namespace ручки политики**: rate limits политики памяти (per-namespace store/recall), квоты на векторы (413 "Namespace vector quota exceeded"), per-namespace конфиг NER (`extract_entities`, `entity_types`) и конфиг extractor [source: таблица ошибок api-notes.md + rate limiting + client.py `configure_namespace_ner`/`get_namespace_entity_config`].

## 5. Команда / multi-agent работа

- Единственное явное заявление про multi-agent — таблица use-case'ов: "Multi-agent pipelines — Shared cross-agent memory, session isolation per agent, importance-ranked recall" [source: https://github.com/Dakera-AI/dakera-deploy/blob/main/README.md, "Used For"]. Механически это значит: агенты с общим `agent_id`/namespace делят память, а per-agent namespaces держат их изолированными [source: api-notes.md "Conventions"; INFERENCE о механизме разделения — ни один документ не показывает отдельный примитив "share with team"].
- Session-механика поддерживает агентов с несколькими сессиями: session-scoped pre-filter HNSW и BM25 session pre-filter предотвращают «протекание» между сессиями ("Session-scoped queries no longer bleed cross-session results") [source: https://github.com/Dakera-AI/dakera-py/blob/main/CHANGELOG.md, запись v0.11.36, CE-52/CE-53].
- Ассоциации knowledge-graph дают структуру между памятями и между агентами: рёбра `related_to`, `shares_entity`, `precedes`, `linked_by`; `memory_link` создаёт явные рёбра; `knowledge_query` (KG-2) выполняет BFS с фильтрами по типам рёбер; `agent_graph_export` экспортирует весь граф агента [source: docstring client.py `memory_graph`/`memory_link`/`knowledge_query`/`agent_graph_export`]. Per-namespace извлечение сущностей GLiNER питает entity-scoped vector-поиск, например `{"tags": F.array_contains("entity:PERSON:alice")}` [source: dakera-py CHANGELOG, запись v0.11.46 ArrayContains].
- Consolidation — это история про «гигиену команды»: `POST /v1/memory/consolidate` (кластеризация DBSCAN или greedy, threshold, dry-run), agent-scoped DBSCAN consolidation с деprecation дубликатов + anchor-памятями, эндпоинты consolidation log/config, плюс `knowledge/summarize` и `knowledge/deduplicate` [source: client.py `consolidate`/`consolidate_agent`/`get_consolidation_log`/`patch_consolidation_config`/`summarize`/`deduplicate`].
- Функциональности team/roles/workspace поверх namespaces + скоуп-ключей в изученных источниках не документировано [INFERENCE: ничего не найдено в README организации, api-notes или поверхности SDK].

## 6. Дополнительные фичи, о которых стоит рассказать

- **Memory types**: `episodic` (по умолчанию), `semantic`, `procedural`, `working` [source: docstring `store_memory` в client.py].
- **Importance + scoring**: importance 0.0–1.0 при store; recall возвращает `score` (ограничен косинусом только при чистом vector-роутинге), `weighted_score` (rerank с весом по importance) и `smart_score = w_vec·relevance + w_imp·importance + w_rec·recency + w_freq·frequency`; scores BM25/hybrid не ограничены; opt-in `DAKERA_NORMALIZE_RELEVANCE=1` [source: api-notes.md, раздел "Scoring"]. Feedback сдвигает importance (upvote/downvote/flag) и decay [source: api-notes.md "Updating memories"].
- **Hybrid routing**: `routing = auto | vector | bm25 | hybrid` на recall, с RRF-фьюжном (`DAKERA_RRF_K` настраивается), pseudo-relevance feedback для temporal/inference-запросов, ML-классификатор запросов, стемминг Snowball для BM25 [source: recall-поля api-notes.md; dakera-py CHANGELOG, записи CE-48/CE-49/CE-58/CE-71].
- **Rerank**: cross-encoder rerank (bge-reranker-v2-m3), `rerank=true` по умолчанию на recall, корректная деградация под нагрузкой [source: recall-поля api-notes.md; dakera-py CHANGELOG CE-13].
- **Knowledge graph / ассоциации (COG-2 / KG-2 в dakera-py)**: обход графа с фильтрами по глубине и типам рёбер, кратчайший путь, явное связывание, BFS query DSL, полный экспорт графа [source: client.py `memory_graph`/`memory_path`/`memory_link`/`knowledge_query`/`agent_graph_export`; `__init__.py` экспортирует "Knowledge Graph types (internal graph — knowledge.rs)" и "KG-2: Graph Query & Export types"].
- **Контекст окрестности**: `include_associated=true` на recall обходит KG в поисках соседних памятей [source: таблица recall-полей api-notes.md].
- **Семейство consolidation**: дедупликация кластеризацией (dbscan/greedy), summarize, deduplicate, логи/конфиг consolidation [source: client.py; api-notes.md].
- **Temporal-фичи**: bi-temporal `valid_from` (сервер v0.11.98+, DAK-7424), авто-извлечение дат в `metadata._dakera_content_date` (v0.11.73+), TTL/`expires_at`, скоринг по временной близости, дашборды метрик memory decay (v0.8.0+) [source: docstring `store_memory` в client.py; раздел store api-notes.md; раздел monitoring README dakera-deploy].
- **Batch + streaming**: batch store (1–1000, один проход embedding), batch recall/forget, SSE-стриминг событий (CE-1) [source: api-notes.md; раздел SSE client.py + `batch_recall`/`batch_forget`].
- **MCP-сервер**: 14 core-инструментов по умолчанию (`dakera_store`, `dakera_recall`, `dakera_search`, `dakera_session_start/end`, `dakera_batch_recall`, `dakera_forget`, `dakera_hybrid_search`, `dakera_fulltext_search`, `dakera_knowledge_graph`, `dakera_extract`, `dakera_batch_forget`, + 2 discovery meta-tools), профили core(14)/admin(32)/power(69)/all(87) для контроля стоимости контекста [source: https://github.com/Dakera-AI/dakera-mcp/blob/main/README.md].
- **Транспорты**: HTTP + gRPC в каждом профиле развёртывания [source: таблица сравнения в README dakera-py; port-маппинги Compose].
- **Ops**: метрики Prometheus, дашборды Grafana (rates запросов, латентность, cache hit ratios, здоровье кластера, decay), HA на 3 узла с gossip + Traefik, ярусное хранилище L1/L2/L3, гайд по backup/restore MinIO [source: README dakera-deploy].

## 7. Бенчмарк LoCoMo

**Что такое LoCoMo.** "Evaluating Very Long-Term Conversational Memory of LLM Agents" — Maharana, Lee, Tulyakov, Bansal, Barbieri, Fang; arXiv:2402.17753 (февраль 2024), ACL 2024. Работа представляет конвейер «машина-человек» для генерации очень долгих диалогов, заземлённых в персонах и временных графах событий, и датасет LoCoMo: очень долгие разговоры — в среднем 300 реплик / 9K токенов, до 35 сессий — с бенчмарком, покрывающим question answering, event summarization и мультимодальную генерацию диалогов [source: https://arxiv.org/abs/2402.17753, abstract]. Репозиторий данных: https://github.com/snap-research/LoCoMo ("ten conversations... annotated for the question-answering and event-summarization tasks") [source: https://github.com/snap-research/LoCoMo README].

**Опубликованные Dakera результаты LoCoMo — они ДЕЙСТВИТЕЛЬНО публикуются, на собственной странице бенчмарка организации и в бейджах README (все цифры ниже — самоотчётные цифры Dakera с этой страницы):**

- Хедлайн: **88.2% Recall@20**, Dakera v0.11.107, оценено в сентябре 2026; "10 conversations, 1,536 evaluated questions, no LLM in the retrieval path"; метрика — retrieval recall, оценённый LLM-judge (правильный ответ присутствует в top-20 найденных памятей) [source: https://dakera.ai/benchmark].
- По категориям: Cat1 Single-hop **86.9%** (282 вопроса); Cat2 Multi-hop **85.4%** (321 q); Cat3 Temporal inference **73.9%** (92 q, сама себя называет самой сложной категорией); Cat4 Open-domain **91.0%** (841 q). В итоговой строке указано "1,536 (10 conversations)... adversarial category excluded" [source: https://dakera.ai/benchmark, таблица разбивки].
- Сверка количества вопросов: всего в LoCoMo 1,540 QA-вопросов; оценивается 1,536 (adversarial-категория исключена), "We do not use sampled subsets" [source: https://dakera.ai/benchmark, Evaluation methodology]. README репозиториев в разных местах говорят "1,536 Q" (README dakera-py) или "1,540 questions" (README dakera-deploy) [source: README dakera-py, таблица "Why Dakera?"; README dakera-deploy, "Why Dakera?"].
- Протокол (самоопубликованный): ingest через `POST /v1/memory` с сохранением границ сессий, без preprocessing/summarization; recall через `POST /v1/recall` с возвратом top-20 с hybrid HNSW+BM25 + не-LLM temporal re-ranker'ом; LLM-judge оценивает бинарное наличие по стандартному evaluation-промпту LoCoMo; 88.2% — среднее по 1,536 вопросам [source: https://dakera.ai/benchmark, "How we evaluate"].
- Заявка по латентности на той же странице: P99 < 10 ms на стороне сервера на прогретом in-memory индексе из 20k векторов (top_k=20, однопоточно, простой 8-ядерный x64-хост; ≈16 ms end-to-end) [source: https://dakera.ai/benchmark, "Production latency"].
- Подача конкурентов (как напечатано у Dakera, другая метрика — QA accuracy, "not directly rankable... context, not a leaderboard"): Letta Filesystem 74.0%, Zep 94.7%, Mem0 92.5%, причём обе цифры Zep/Mem0 описаны как активно оспариваемые другой стороной [source: https://dakera.ai/benchmark, "How Dakera compares" + "The benchmark dispute"].
- Историческая точка данных в changelog SDK: более ранний полный прогон на 1540 вопросов на сервере v0.11.32–v0.11.36 дал **82.4% overall** (Cat1 80.1%, Cat2 85.7%, Cat3 55.2%, Cat4 85.0%) [source: https://github.com/Dakera-AI/dakera-py/blob/main/CHANGELOG.md, запись v0.11.36 (2026-04-26), пункт CE-53].
- **Где НЕ опубликовано**: ни в одном репозитории организации нет harness, скриптов или файлов результатов бенчмарка — нет каталога `benchmarks/`, только бейджи и маркетинговая страница [source: https://api.github.com/orgs/Dakera-AI/repos + список содержимого репозитория dakera-deploy, проверено 2026-09-27]. Оговорка для README: цифры самоотчётные от вендора, сторонней верификации в изученных источниках не найдено [INFERENCE о статусе верификации; сами цифры процитированы выше].
